본 가이드는 **셰르파 앱에 멀티 에이전트 개발 환경을 실제로 구축**하기 위한 단계별 실행 가이드입니다. 기술 문서 `claude-code-multi-agent-guide.md`의 개념을 실제 작업으로 전환하는 방법을 설명합니다.

#### 1. 필수 지식
- **Claude Code 기본 사용법**: 최소 1주일 이상 사용 경험

- **Riverpod 기초**: Provider 개념과 의존성 이해
- **Flutter 개발 경험**: 중급 이상

#### 2. 필수 문서
- ✅ `CLAUDE.md` - 셰르파 앱 전체 가이드
- ✅ `claude-code-multi-agent-guide.md` - 멀티 에이전트 기술 문서
- ✅ `implementation_vs_reference_analysis.md` - 구현 분석

#### 3. 개발 환경
- **IDE**: VS Code + Claude Code 플러그인 또는 Claude.ai
- **Git**: 버전 관리를 위한 Git 설치
- **Flutter SDK**: 3.27.0 이상
- **충분한 시간**: 방해받지 않는 4-6시간 블록

### ⚠️ 주의사항

#### 시작 전 확인사항
```
✅ 현재 작업 중인 코드가 모두 커밋되어 있나요?

- **과도한 의존**: 에이전트를 맹신하지 말고 검증 필수

```

**현재 상태 확인**:
```

2. main 브랜치가 최신인가? → pull 받기

```

#### 주의사항
- ⚠️ main 브랜치에서 직접 작업하지 마세요

### Step 1.2: .claude 폴더 구조 생성 (10분)

#### 왜 필요한가?
Claude Code는 `.claude` 폴더를 특별하게 인식합니다. 이 폴더 안의 설정 파일들이 에이전트의 "두뇌"가 됩니다.

#### 어떻게 하나?

**폴더 구조 생성**:
```
프로젝트 루트 (C:\sherpa_app)에서:

.claude/
├── agents/
│   ├── core/              ← 핵심 에이전트 (필수)
│   ├── specialists/       ← 전문 에이전트 (선택)
│   └── support/          ← 보조 에이전트 (선택)
├── workflows/            ← 워크플로우 정의
├── standards/            ← 코딩 표준 및 규칙
└── README.md            ← 전체 시스템 개요
```

**의미 설명**:

1. **agents/core/**
   - Architecture Guardian, Feature Developer, Test Engineer, Code Reviewer
   - 모든 작업에 필요한 필수 에이전트
   - 가장 먼저 구축해야 함

2. **agents/specialists/**
   - Gamification Expert, State Management Expert, UI/UX Specialist
   - 특정 작업에만 필요한 전문 에이전트
   - 선택적으로 구축

3. **agents/support/**
   - Documentation Writer, Performance Analyzer
   - 보조적인 역할
   - 나중에 추가 가능

4. **workflows/**
   - feature-development.md, gamification-changes.md 등
   - 에이전트들을 조합한 작업 흐름 정의

5. **standards/**
   - sherpa-app-rules.md, coding-standards.md
   - 모든 에이전트가 따라야 할 규칙

#### 주의사항
- ⚠️ 폴더명은 정확히 `.claude` (점 포함)
- ⚠️ 대소문자 구분 (agents, workflows, standards)
- ⚠️ Windows에서는 폴더 생성 시 점(.)으로 시작하는 이름 주의

#### 검증 방법
```
1. .claude 폴더가 프로젝트 루트에 있나?
2. 하위 폴더 5개가 모두 생성되었나?
3. Git에서 .claude 폴더를 인식하나?
```

### Step 2.1: Architecture Guardian 구축 (1시간)

#### 왜 가장 먼저 구축하나?

Architecture Guardian은 **모든 다른 에이전트의 기초**입니다. 이 에이전트가 없으면:
- Provider 순서 오류로 앱 크래시
- Feature-First 구조 깨짐
- Navigation 패턴 혼란

셰르파 앱처럼 복잡한 상태 관리를 가진 프로젝트에서는 **필수 중의 필수**입니다.

---

#### 이해하기: Architecture Guardian의 역할

**비유로 설명**:
Architecture Guardian은 건물의 **구조 엔지니어**입니다.

```
집을 지을 때:
- 기둥을 먼저 세우고 벽을 세워야 함 (Provider 순서)
- 방마다 용도가 정해져 있음 (Feature-First 구조)
- 출입문은 정해진 위치에만 (Navigation 패턴)

이걸 어기면:
→ 집이 무너짐 (앱 크래시)
→ 나중에 고치기 매우 어려움
```

**셰르파 앱에서의 역할**:

1. **Provider 초기화 순서 검증**
   ```
   실제 사례:
   - relationshipProvider를 sherpiProvider보다 먼저 초기화
   → 앱 시작 시 바로 크래시
   → Architecture Guardian이 이를 사전에 차단
   ```

2. **Feature-First 구조 보호**
   ```
   실제 사례:
   - 개발자가 급하게 lib/providers/temp_provider.dart 생성
   → 나중에 features/quests/로 옮기기 번거로움
   → Architecture Guardian이 처음부터 올바른 위치 안내
   ```

3. **Navigation 안전성**
   ```
   실제 사례:
   - 모임 상세 화면에 MeetingModel 객체 직접 전달
   → 웹에서 작동 안 함, 딥링크 깨짐
   → Architecture Guardian이 ID 전달 방식 강제
   ```

**Step 2.1.2: Identity 정의 (5분)**

에이전트에게 **정체성**을 부여합니다. 이것이 에이전트의 행동을 결정합니다.

```markdown
## Identity
당신은 **Architecture Guardian**입니다.
셰르파 앱의 아키텍처 무결성을 보호하는 것이 당신의 신성한 임무입니다.

당신은:
- 엄격하지만 공정합니다
- 설명을 명확하게 제공합니다

## Core Knowledge Base

### 셰르파 앱 Provider 의존성 그래프

이것은 **절대 불변의 법칙**입니다:

```
Level 0 (독립):
└── globalGameProvider

Level 1 (게임 데이터 의존):
└── globalUserProvider → globalGameProvider

Level 2 (유저 데이터 의존):
├── globalPointProvider → globalUserProvider
├── globalUserTitleProvider → globalUserProvider
├── questProviderV2 → globalUserProvider
├── globalMeetingProvider → globalUserProvider
└── emotionAnalysisProvider → globalUserProvider

Level 3 (복합 의존):
├── sherpiProvider → globalUserProvider + emotionAnalysisProvider
└── relationshipProvider → sherpiProvider + globalUserProvider
```

**초기화 순서 (lib/main.dart)**:
1. globalGameProvider
2. globalUserProvider
3. globalPointProvider
4. globalUserTitleProvider
5. questProviderV2
6. globalMeetingProvider
7. emotionAnalysisProvider  ← sherpiProvider보다 먼저!
8. sherpiProvider
9. relationshipProvider

**왜 이 순서인가?**
- Level 0부터 Level 3까지 순차적으로
- 같은 Level 내에서는 순서 무관
- 하지만 relationshipProvider는 맨 마지막 (모든 것에 의존)
```

**실제 예시로 설명**:

잘못된 순서:
```

ref.read(sherpiProvider);         // Level 3

→ ERROR: relationshipProvider가 sherpiProvider를 찾지 못함
```

올바른 순서:
```
ref.read(sherpiProvider);         // Level 3 먼저
ref.read(relationshipProvider);   // 그 다음

```

# Gamification Expert

## Identity
당신은 셰르파 앱의 **Gamification Expert**입니다.

## 핵심 지식

### 셰르파 앱 게임 공식

**1. 등반력 (Climbing Power)**
```
최종 등반력 = 기본 등반력 × (1 + 능력치%) × (1 + 뱃지%)

기본 등반력 = (레벨 × 10) + 칭호보너스

칭호 보너스:
- Lv 1-9: +0
- Lv 10-19: +50
- Lv 20-29: +120
- Lv 30-39: +250
```

**2. 성공 확률**
```
성공 확률 = 기본 확률(등반력 비율) + 의지 보정 + 뱃지
의지 보정 = (의지% / 100) × 0.1

예시:
- 등반력 150, 산 요구 100, 의지 50%
→ 기본 확률 0.8 + 0.05 = 0.85 (85%)
```

**3. XP 보상**
```
성공 XP = 시간 × 32.5 × 난이도곡선
실패 XP = 성공 XP × 0.25
```

**4. Point 보상**
```
성공 Point = 시간 × 30.0 × 난이도곡선
```

### 포인트 이코노미 현황

**주요 획득 경로**:
- 일일 퀘스트 전체: 50p
- 주간 어려운 퀘스트: 100p
- 모임 참석: 100p
- 모임 호스팅: 300p
- 레벨업: 100p

**주요 소비 경로**:
- 프리미엄 퀘스트 팩: 2,000p
- 분석 리포트: 1,000p
- 퀘스트 완료 티켓: 500p

**균형 지표**:
- 평균 일일 획득: ~200-300p (활동적 유저)
- 프리미엄 팩 회수 기간: 7-10일

## 검증 및 문제 해결

### 🔍 시스템 검증 체크리스트

#### Level 1: 기본 구조 검증

```
□ .claude 폴더가 존재하는가?
□ agents/, workflows/, standards/ 폴더가 있는가?
□ README.md가 있는가?
□ Git에 커밋되었는가?
```

#### Level 2: 에이전트 파일 검증

```
□ 각 에이전트 .md 파일이 존재하는가?
□ YAML frontmatter가 올바른가?
□ Identity 섹션이 명확한가?
□ 핵심 지식이 포함되어 있는가?
□ 검증 규칙이 구체적인가?
```

#### Level 3: 작동 검증

```
□ Architecture Guardian이 Provider 순서를 검증하는가?
□ Feature Developer가 패턴을 준수하는가?
□ Test Engineer가 테스트를 작성하는가?
□ Code Reviewer가 품질을 검증하는가?
```

#### Level 4: 효과 검증

```
□ 작업 시간이 단축되었는가? (목표: 30%+)
□ 버그 발견이 빨라졌는가? (목표: 75%+ 초기 발견)
□ 코드 품질이 일관되었는가?
□ 팀원들이 만족하는가?
```

### 🔧 문제 해결 가이드

#### 문제 1: 에이전트가 작동하지 않음

**증상**:
```
Claude Code에서 "Use Architecture Guardian..."라고 해도
에이전트가 제대로 작동하지 않음
```

**원인 진단**:
1. `.claude/agents/core/architecture-guardian.md` 파일이 있는가?
2. YAML frontmatter가 올바른가?
3. 파일 이름이 정확한가? (대소문자, 하이픈)

**해결 방법**:
```
1. 파일 존재 확인
2. YAML 문법 검증 (온라인 YAML validator 사용)
3. Claude Code 재시작
4. 다시 시도
```

---

#### 문제 2: 에이전트가 셰르파 앱을 이해하지 못함

**증상**:
```
에이전트가 일반적인 조언만 하고
셰르파 앱 특정 상황을 고려하지 못함
```

**원인**:
에이전트의 Core Knowledge Base가 불충분함

**해결 방법**:
```markdown
에이전트 .md 파일에 추가:

## 셰르파 앱 특정 정보

### Provider 목록
[9개 Provider와 의존성 설명]

### 주요 패턴
1. ModernColors 사용
2. Activity Completion 통합
3. Null Safety

### 일반적인 실수
[팀에서 자주 하는 실수 나열]
```

---

#### 문제 3: 프롬프트가 너무 길어짐

**증상**:
```
매번 긴 프롬프트를 작성해야 해서 번거로움
```

**해결 방법 1: 워크플로우 문서화**
```
자주 사용하는 패턴을 워크플로우로 저장:
.claude/workflows/point-reward-change.md

그리고:
"Execute point-reward-change workflow for daily quest"
```

**해결 방법 2: 에이전트에 기본값 설정**
```markdown
에이전트 .md에 추가:

## Default Behavior

컨텍스트가 명시되지 않으면:
- 셰르파 앱 기준으로 판단
- CLAUDE.md 참조
- Feature-First 구조 가정
```

---

#### 문제 4: 에이전트 간 충돌

**증상**:
```
Architecture Guardian: "Provider 추가 필요 없음"
State Management Expert: "새 Provider 추가 권장"
```

**해결 방법**:
```
우선순위 규칙 적용:
1. Architecture Guardian > 다른 모든 에이전트
2. 전문 에이전트 > 일반 에이전트
3. 의견 충돌 시 사람이 최종 결정

에이전트 .md에 명시:
"Architecture Guardian의 결정이 최우선입니다"
```

---

#### 문제 5: 팀원이 사용하지 않음

**증상**:
```
구축했지만 나만 사용하고 팀원은 기존 방식 고수
```

**원인**:
- 학습 곡선
- 익숙함에 대한 선호
- 효과를 체감하지 못함

**해결 방법**:
```
1. 작은 성공 사례 공유
   "이번에 에이전트 덕분에 Provider 버그 사전 발견"

2. 페어 프로그래밍
   함께 작업하며 사용법 시연

3. 선택적 도입
   강제하지 말고 필요한 사람만 사용

4. 피드백 반영
   팀원 의견 듣고 개선

5. 점진적 확산
   1명 → 2명 → 팀 전체
```
